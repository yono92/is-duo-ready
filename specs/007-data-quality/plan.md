# 구현 계획

11. 12:36 사용자 결정에 따라 KR Lookup의 유효한 정상 notFound를 국내 부재 기준으로 사용한다. FilmN 2개의 현재 API 결과를 확인하고 새 운영 백업에서 기존 보관 함수를 dry-run/apply한다. 웹 404 조건은 요구하지 않는다. 기존 근거·이력·지원 상태와 나머지 공개 앱을 보존하고, 익명 행/아이콘/이력 차단·ko/en not-found 응답·집계·정합성·재실행 해시 불변을 검증한다. HTTP/파싱 오류를 notFound로 승격하거나 스케줄러를 활성화하지 않는다.

10. 12:15 듀오 지원 재검사: 새 운영 스냅샷에서 보관 제외 전체 ID를 고정하고 새 KR Lookup 및 제품 페이지 본문/버전/명시적 배지를 다시 수집한다. 기존 원문 인용을 재관측하고 모든 상태의 변경 후보를 비교한다. 제품 신원·국가·추천/호환 정보 제외·다국어 키워드 경계를 검증하고 모호한 후보는 공식 개발사·Apple 출처를 보완한다. 원문 직접 검토 후 지원 정정은 기존 save/publish 배치로 dry-run/apply하고, 재실행·이력·기존 근거·익명 초안/보관·운영 ko/en 응답을 검증한다. 스키마·배포·새 앱 등록은 변경하지 않는다.

9. 한국 배포 여부 후속 점검: 운영 백업과 고정 ID 3개의 현재 notFound/404를 확인한 뒤 기존 보관 트랜잭션을 dry-run/apply한다. 나머지 전체 앱의 고정 모집단에서 KR Lookup 및 동시 최대 6개·배치 간 750ms 간격의 한국 제품 페이지 응답을 검사한다. HEAD 미지원은 GET으로 보완하고, 응답 불일치·오류는 개별 재조회/제품 신원 확인으로 판별한다. 추가 목록 자동 제거는 하지 않는다. 보관한 3개의 익명 행·아이콘·이력 차단, 공개 상세 not-found 신호·앱 본문 미노출, 기존 지원 수·근거 보존, 재실행 해시 불변과 정합성을 확인한다. 스트리밍 후 notFound는 HTTP 200을 유지할 수 있으므로 설치된 Next.js 문서와 실제 digest/noindex 응답을 기준으로 검증한다.

1. `scripts/lib/content-quality.ts`의 버전 관리 SQL 규칙과 `scripts/check-data.ts` 읽기 전용
   CLI를 작성한다. 호스팅 대상·프로젝트 일치와 비공개 설정을 재사용한다. REPEATABLE READ
   READ ONLY에서 읽고 실행 결과·규칙 코드 해시를 `.data/quality/`에 0600으로 남긴다.
2. 공개 스냅샷과 편집 초안을 구별한다. 공개 근거는 스냅샷에 남은 evidence ID와 보존된
   공식 자료로 확인한다. 초안 연결 변경을 공개 근거 소실로 오인하지 않는다. 보류·fallback은 경고다.
3. `DirectoryResult.stats`와 합계 검증을 추가한다. 실제 SQL은 공개 KR 집합→검색 집합→
   페이지→정렬/아이콘→집계를 한 문장에서 계산한다. 개인정보·초안 테이블을 공개 집계에 쓰지 않는다.
4. 홈에 스토어·총수, 상태별 비율 막대와 의미 있는 dl/dt/dd 범례를 추가한다.
   최신 사용자 선택에 따라 Recharts를 별도 클라이언트 번들로 로드한다. 정확한 버전을
   고정하고 Vega 의존성을 제거하며 Astryx core는 유지한다. SVG 가로 정규화 누적 막대와
   Astryx 데이터 색상·툴팁 표면을 사용한다. 집계·범례는 서버에서 제공한다.
   국제화 숫자·라벨·모집단 설명으로 검색 결과 수와 전역 수를 구별한다.
5. 단위·격리 DB·브라우저 검증과 실제 운영 읽기 전용 대조를 수행한다. DB 정정·마이그레이션·
   신규 프로젝트·배포·스케줄러는 필요하지 않다. 앱 수와 근거 판정은 보존한다.

원칙 점검: 공식 근거 판정을 변경하지 않고 published-only/RLS·locale/country·fixture 경계를
유지한다. 숫자 불일치와 조회 실패를 숨기지 않고 반복 가능한 검사와 실제 실행 결과를 남긴다.

6. 전체 공식 자료 재조회: 기존 운영 DB의 1,000개 ID와 근거를 읽기 전용 스냅샷으로 고정한다.
   `rescan-app-evidence.ts`는 기존 제한·검증·재시도 경로로 최대 20개씩 KR Lookup을 읽는다.
   `rescan-app-pages.ts`는 동시 2개·배치 간 750ms 간격으로 공개 제품 페이지를 읽고 해당 앱의
   설명·제품 메타데이터·포함된 버전 기록만 추출한다. 미완료/실패만 재개하며 키워드는 판정이 아니다.
   새 공식 근거와 기존 근거의 재관측 여부, 보류 사유 및 검토 범위를 앱별 자료로 남긴다.

7. 2026-11-02 갱신: 기존 호스팅 설정과 contentSnapshot으로 기준·백업을 고정한다. 새 날짜의
   전체 및 카테고리 차트와 기존 앱 원문을 수집하고 ID·KR·출처·순위·시각을 검증한다.
   후보는 키워드 자동 판정 없이 검토한다. 사용자가 승인한 1,000개 초과를 허용한 명시적
   배치에서 신규 앱과 지원 근거 변경을 기존 함수로 반영하고 나머지 공개 스냅샷·기존 근거를 보존한다.
   동일 배치 재실행의 콘텐츠 무변경과 최종 익명 집계를 검증하고 실제 수치와 제한을 기록한다.

8. 2026-11-03 갱신: 운영 콘텐츠를 새 기준 스냅샷으로 백업하고 당일 조회 자료를 재사용해 전체 제품 페이지 및 46개 차트를 재조회한다. 누락 앱과 검토 완료한 지원 근거를 명시적 배치로 반영하고 기존 근거와 비공개 편집을 보존한다. 최신 버전 정보와 공개 지원 정정의 검증을 분리하며 같은 배치 재실행의 불필요한 이력·시각 변경을 차단한다.

   전체 제품 페이지는 당일 고정 배치의 로컬 실행 사본에서 동시 요청을 최대 6개로 제한해 재개한다. 기존 페이지 신원·본문 제한·재시도·원문 해시·원자적 manifest 저장은 그대로 사용하고 429/서버 오류의 대기를 유지한다. 영구 수집기 설정은 변경하지 않는다.

   일반 버전 메타데이터는 전용 트랜잭션에서 listing과 공개 스냅샷의 currentVersion만 갱신한다. 지원 관련 필드·근거·reviewedAt·supportChangedAt·지원 이력은 바이트/값 대조로 보존하고 별도의 비공개 수집 provenance를 남긴다. 지원 정정은 save_app/publish_app을 사용한다.
