## 1. 서비스 목적

2026-10-29 사용자 추가 요청: 로컬 홈 기기 영역에 회전·접힘을 직접 조작하는 3D 콘셉트를 제공한다. 드래그 및 키보드 회전, 접힘 각도, 초기화를 지원한다. 실측 제품이나 앱 지원 근거로 표시하지 않으며 기존 개발 기기 자산의 배포 차단을 유지한다.

아이폰 듀오 사용자와 구매 예정자가 자신이 사용하는 앱의 듀오 최적화 여부를 검색하고, 최적화 내용과 공식 근거를 확인하는 다국어 앱 디렉터리다. 초기 표시 언어는 한국어·영어를 제안하며, 데이터 수집 지역은 한국 앱스토어로 시작한다.

참고 서비스 Is Apple Silicon Ready의 지원 현황 탐색 목적을 계승하되, 공개 UI의 탐색 구조는 Notion Connections를 참고한 카드형 디렉터리로 설계하고, 시각 표현은 사용자가 지정한 getdesign.md의 Apple 디자인 분석을 참고한다. 단순 실행 가능 여부를 듀오 최적화로 간주하지 않는다. 공식 정보와 운영자의 실기기 확인은 별도 근거로 다룬다.

### 핵심 사용자 질문

1. 이 앱이 듀오에 최적화됐는가?
2. 펼친 화면이나 접힘 자세에서 어떤 기능이 달라지는가?
3. 어떤 공식 자료와 버전을 근거로 판단했는가?
4. 정보는 언제 확인됐으며 이후 무엇이 변경됐는가?

### 확정 사항

| 항목 | 결정 |
| --- | --- |
| 프런트엔드 | Next.js App Router, TypeScript |
| UI | Astryx, Tailwind CSS |
| DB·관리자 인증 | Supabase Postgres, Supabase Auth |
| 배포 | Vercel |
| 개발 프로세스 | GitHub Spec Kit 기반 명세 주도 개발 |
| 디자인 기준 | Notion Connections의 카드형 탐색 구조 + getdesign.md Apple 디자인 분석 기반 시각 표현; 적용 규칙은 DESIGN.md |
| 기기 비주얼 | 홈에 펼쳐진 듀오의 형태와 화면이 드러나는 이미지 필수 |
| 테마 | 라이트 / 다크 단일 switch; 첫 방문은 시스템 자동 |
| 다국어 | 첫 버전 필수. 초기 한국어·영어를 제안하며 추가 언어 확장 가능 |
| 데이터 지역 | 한국 앱스토어 우선; 표시 언어와 별도 관리 |
| 데이터 전략 | 후보 약 200개 확보 → 검토한 앱 약 100개로 공개 |
| 판정 원칙 | 공식 출처 중심, 관리자 검토 후 공개 |

100개는 조사·공개 목표이며 공식 지원 앱 100개를 보장한다는 의미가 아니다. 10개는 수집 방식 검증용 샘플 수량이며 출시 규모가 아니다.

## 2. MVP 범위

### 포함

- 앱 검색, 한글·영문 별칭, 카테고리·지원 상태 필터, 정렬, 페이지 이동.
- 앱 상세, 공식 출처, 지원 확인 버전, 확인 날짜, 변경 이력.
- 최근 지원 현황 업데이트 목록.
- 관리자 인증, 앱·근거 편집, 변경 후보 검토, 공개 및 정정.
- 앱스토어 URL 및 CSV를 통한 일괄 등록, 중복 방지.
- 수집 가능한 공식 출처의 정기 확인과 실패 기록.
- 비회원 앱 추가·정보 수정 제보.
- 모든 사용자·관리자 화면의 반응형, 라이트·다크 모드, 한국어·영어 UI.
- 언어별 URL, 언어 전환, UI 메시지 및 공개 콘텐츠 번역 구조.

### 후속 범위

일반 사용자 계정, 즐겨찾기·개인 알림, 댓글·별점, 한국어·영어 외 언어, 다른 기기 지원, 앱 비교, AI 자동 분류, 운영자 실기기 평가 전용 화면은 후속 기능이다. 초기 공개에 필수인 운영 도구를 이들보다 우선한다.

## 3. 정보 판정 정책

### 공개 지원 상태

| 코드 | 표시 | 판정 기준 |
| --- | --- | --- |
| supported | 공식 지원 | 공식 출처가 현재 제공 중인 듀오 대응을 명시 |
| planned | 지원 예정 | 공식 출처가 향후 지원을 예고 |
| unknown | 미지원 · 근거 미확인 | 지원 근거 미확인 상태로 초기 목록에 공개; 공식 미지원과 구분 |
| unsupported | 미지원 확인 | 개발사가 현재 미지원을 명확히 안내 |

- 2026-10-29 최신 사용자 결정: 초기 등록 128개를 공개한다. 공식 지원 문구가 확인된 22개는 지원, 나머지 106개는 `unknown`을 유지하며 “미지원 · 근거 미확인”으로 표시한다. 미확인을 공식 미지원(`unsupported`)으로 바꾸거나 근거를 만들지 않는다.
- 지원 상태와 발행 상태(draft/published/archived)를 분리한다.
- 지원·예정·미지원 판정에는 공식 근거가 필수다. 확인 필요에는 조사 메모 및 검토 날짜가 필요하다.
- 애플 소개 기사에 앱 이름이 나온 것만으로 현재 지원으로 분류하지 않는다. 예정 시점, 지역, 배포 문구를 확인한다.
- 최신 앱 버전과 지원이 확인된 버전을 별도 저장한다. 버전이 명시되지 않으면 '버전 미공개'로 표시한다.
- 넓은 화면 배치, 접힘 자세 활용, 화면 전환 대응 등 기능 태그는 출처가 뒷받침하는 경우에만 사용한다.
- iPad 지원, 일반 iPhone 호환성, 화면 분할 가능 여부만으로 듀오 최적화를 추정하지 않는다.
- 자동 수집 성공 시각은 운영자 최종 확인 시각을 갱신하지 않는다.
- 최신 릴리스 노트에서 듀오 문구가 사라져도 이전 지원 근거를 삭제하지 않는다.
- 공식 지원이지만 실사용 문제가 제보된 경우 제보를 따로 검토한다. 제보만으로 공식 지원 여부를 즉시 뒤집지 않는다.

### 출처 우선 사용

앱스토어의 명시적 배지·업데이트 설명, 개발사 공식 공지·문서, Apple 공식 발표를 근거로 사용한다. 검색 결과 요약과 언론 기사, 커뮤니티는 발견 경로이며 단독 판정 근거가 아니다. 출처가 충돌하면 시점·버전·지역을 비교하고 해소 전까지 확인 필요로 둔다.

### 공식 듀오 배지 확인 앱의 공개 — 2026-10-29 사용자 결정

- 사용자는 Apple App Store의 `Made for iPhone Duo` 공식 배지가 확인된 앱의 즉시 공개를 승인했다. 해당 앱은 배지를 공식 지원 근거로 사용하며 별도 실기기 평가나 앱별 추가 공개 승인을 기다리지 않는다.
- 앱 ID·한국 스토어 배포·공식 출처 URL·실제로 관찰한 배지 문구와 확인 시각을 기록한다. 설명·번역·분류 등 기존 공개 필수 항목을 갖추고 출처 충돌이 없으면 기존 공개 트랜잭션으로 반영한다. 배지가 명시하지 않는 최초 지원 버전·세부 기능·품질 평가는 추정하지 않는다.
- 기존 릴리스 노트 근거 22개, Apple 컬렉션 수록, 다운로드 버튼, 자체 지원 상태 표시를 배지 관측으로 바꾸지 않는다. 웹/API에서 배지가 보이지 않는 경우는 미확인이며 배지가 없거나 미지원이라는 뜻이 아니다.
- 관측 수행자와 사용자의 공개 승인 근거를 구분해 남긴다. 수집 시각을 사람이 앱별로 검토한 시각으로 만들어 넣지 않는다. 상시 수집기의 자동 공개 기능을 활성화한 것으로 해석하지 않는다.

Apple의 [개발자 안내](https://developer.apple.com/news/?id=kkphp5qo)는 듀오 스크린샷 제출 시 제품 페이지에 최적화를 알리는 배지가 표시된다고 설명한다. 이는 배지의 의미를 설명하는 출처이며 특정 앱의 배지 존재를 증명하지 않는다.

## 4. 정보 구조 및 화면

| 경로 제안 | 화면 |
| --- | --- |
| `/` | 소개, 듀오 이미지, 검색·필터, 앱 목록 |
| `/apps/[slug]` | 앱 상세 및 공개 이력 |
| `/updates` | 지원 정보의 최근 공개 변경 |
| `/submit` | 앱 추가·정보 수정 제보 |
| `/methodology` | 판정 기준 및 독립 서비스 안내 |
| `/admin` | 운영 현황 |
| `/admin/apps` | 앱 관리·가져오기 |
| `/admin/reviews` | 변경 후보 검토 |
| `/admin/submissions` | 제보 검토 |
| `/admin/collections` | 수집 결과·실패 확인 |

표의 경로는 언어 접두사를 생략한 논리 경로다. 실제 화면 URL은 `/ko`, `/en`, `/ko/apps/[slug]`처럼 구성한다. 관리 화면도 언어 접두사를 적용한다. API·인증 콜백은 UI 언어 경로와 별도로 설계한다.

### 홈

- 공개 문구 정리(2026-10-29): 홈은 앱별 듀오 지원 여부를 찾는 목적을 직접 설명한다. 추상적인 슬로건과 반복 소개는 제거하며, 제휴 관계 안내는 푸터에 한 번 표시한다. 지원 안내는 실제 네 가지 상태명과 정의, 공식 배지를 포함한 확인 자료, 정보 갱신 및 한국 스토어 기준을 설명한다.
- 전 화면 문구 검토(2026-10-29): 공개·관리자 화면, 빈 결과·오류·제보·가져오기·수집, 접근성 라벨과 가상 앱 설명까지 한국어·영어를 검토한다. 명확한 라벨과 공식 분류명은 유지하고 추상적인 비유·내부 기능 번호·불필요한 운영 지시는 제거한다. 안내는 실제 상태와 가능한 다음 행동을 설명해야 하며, 완료 상태에서 시작을 권하거나 수집 성공만으로 새 변경이 있다고 단정하지 않는다.
- 헤더: 서비스명, 앱 탐색, 최근 업데이트, 제보, 테마 선택.
- 상단: 소개 문구와 펼쳐진 듀오 이미지. 데스크톱 기본 화면에 검색 영역과 목록 일부가 드러나도록 높이를 제한한다.
- 공통 콘텐츠 최대 폭은 1120px이다. 데스크톱 왼쪽 168px 사이드바에 카테고리·지원 상태를 모으고, 오른쪽 카드 열의 상단에 검색·정렬을 정렬한다. 결과 수 행은 간결하게 둔다.
- hero는 데스크톱에서 글과 기기를 1.15:0.85 비율로 배치하고, 모바일에서는 중앙 정렬한 수직 구성과 150px 기기 영역을 사용한다.
- 모바일은 카테고리와 필터를 Sheet에 배치하고 적용 개수 및 초기화 버튼 제공.
- 검색은 앱 이름·영문명·별칭 대상으로 수행한다. 검색어 및 필터·정렬·페이지는 URL에 보존한다.
- 카테고리는 Apple 공식 명칭 중 생산성, 그래픽 및 디자인, 음악, 도서, 여행, 내비게이션, 사진 및 비디오, 엔터테인먼트, 라이프스타일 9개를 초기 목록에 사용한다. 전체 App Store 분류 체계는 아니며 내부 URL slug는 Apple API 식별자가 아니다. [분류 기준](references/app-store-categories.md)에 출처와 매핑을 기록하고 기존 `category=creativity` URL은 `graphics-design`으로 정규화한다.
- 초기 정렬: 공식 지원 우선, 같은 그룹은 지원 정보 확인일 내림차순. 정렬 선택지: 최근 지원 정보 변경, 이름순.
- 필터 변경 시 첫 페이지로 돌아간다. 초기 페이지 크기는 24개를 제안한다.
- 검색 결과 없음: 검색어·필터 초기화 및 앱 추가 요청 동선 제공.
- DB 오류와 실제 결과 없음은 다른 상태로 표시한다.

### 앱 카드

아이콘, 앱 이름, 개발사, 지원 상태 Badge, 최적화 요약, 최종 확인 날짜를 표시한다. 카드 상단은 아이콘과 이름을 가로로 배치하고, 14px 요약을 최대 두 줄로 축약한 뒤 지원 배지·카테고리 행과 검토일 footer를 둔다. 전체 요약은 상세에서 확인한다. 데이터가 없으면 임의 설명을 만들지 않는다. 카드 전체가 상세 페이지로 이동하는 접근 가능한 링크다. 데스크톱 3열, 태블릿 2열, 모바일 1열을 기본으로 실제 콘텐츠 폭에 맞춰 조정한다.

### 앱 상세

1. 앱 이름·개발사·아이콘·앱스토어 링크.
2. 현재 지원 상태, 확인된 기능 및 요약.
3. 지원 확인 버전, 현재 스토어 버전, 한국 스토어 기준, 최종 검토일.
4. 공식 출처: 제목, 날짜, 짧은 근거 발췌, 외부 링크.
5. 공개 변경 이력과 수정 제보 링크.

확인된 실제 스크린샷이 있으면 사용 조건과 출처를 기록하고 추가한다. 자료가 없는 앱에 합성된 최적화 화면을 증거처럼 노출하지 않는다. 앱 설명과 외부 입력은 HTML로 무조건 렌더링하지 않는다.

## 5. 디자인과 테마

### 시각 방향

카드형 디렉터리 구조를 유지하며 시각 디자인은 Apple 독립 분석, 실제 공개·관리자 컴포넌트는 Meta Astryx 0.7.4를 사용한다. Neutral은 기본 테마이며 Apple 참고의 제품 토큰을 적용한다. `DESIGN.md`가 구체적인 기준이며 이전 Neutral 기본 스타일만 사용한다는 지침은 철회한다.

- 색상·타이포·모서리는 중앙 Apple 참고 토큰으로 관리한다. 입력·키보드·상태·로딩은 실제 Astryx가 담당한다. 첫 화면 등장·카드 반응은 짧고 절제하며 reduced motion에서는 끈다. Tailwind는 제품 배치와 반응형을 담당한다.
- 입력은 TextInput, TextArea, Selector, CheckboxInput, DateInput, FileInput을 사용한다. 숨겨진 폼 데이터 외에 네이티브 입력을 Field로 감싸는 방식은 사용하지 않는다.
- Button, Link, TopNav, SideNavItem, Pagination, Card, ClickableCard, Badge, Dialog, DropdownMenu, Switch, Collapsible, Banner, EmptyState, ProgressBar, Skeleton을 해당 UI에 사용한다.
- 서버 액션·FormData·필수 검증·초기화를 유지하고 파일 선택 및 날짜 변경을 저장까지 검증한다.
- 시스템 글꼴 fallback, 최대 1120px 폭, 1/2/3열 반응형, 히어로 및 카드 정보 위계는 유지한다. 기존 로고·기기 렌더·공식 App Store 배지는 자산 정책을 따른다.
- 한국어·영어 메시지와 공식 Astryx ko-KR 카탈로그를 적용한다. 언어 선택은 Globe 메뉴, 테마는 단일 Switch로 제공한다.
- 키보드 초점·폼 라벨·터치 영역·대비를 확인하고 URL 상태, 데이터와 자산의 정직성을 유지한다.

### 테마 동작

첫 방문은 시스템 설정과 OS 설정 변화를 자동으로 따른다. 사용자는 단일 switch로 라이트·다크를 전환하며 수동 선택은 재방문에도 유지한다. 수동 선택 이후에는 OS 설정 변화를 따르지 않는다. 시스템은 초기 자동 동작이며 별도의 선택 UI는 제공하지 않는다. 첫 로딩 테마 깜빡임과 hydration 오류를 방지한다. 관리자도 동일하게 적용한다.

### 듀오 이미지

홈에 듀오 화면을 보여주는 비주얼은 필수다. Apple 공식 제품 이미지를 우선 후보로 검토하되 사용·편집 조건 확인 전에는 재사용 권한이 있다고 간주하지 않는다. 사용할 수 있는 자산을 확보하지 못하면 독자적인 기기 목업을 제작한다. 목업의 화면은 '화면 예시'로 표시하고 실제 앱의 최적화 증거와 구분한다.

이미지 URL·출처·사용 조건·대체 텍스트를 자산 기록에 남긴다. 두 테마에서 자연스럽게 표시하고 크기를 예약해 레이아웃 이동을 방지한다. 개발 중에는 교체 가능한 자리표시자를 사용해 구현을 계속할 수 있으나 공개 전에는 최종 자산을 준비한다.

### 다국어 요구사항

- 한국어·영어를 초기 구현 언어로 제안한다. 다국어 자체는 확정 요구사항이며 추가 언어는 번역 자료 확보 후 확장한다.
- 루트 진입 시 저장된 언어 선택을 우선하고, 없으면 브라우저 언어를 참고한다. 지원되지 않는 언어는 영어로 연결한다. 직접 접속한 언어 URL은 자동으로 바꾸지 않는다.
- 언어 전환 시 현재 앱 상세, 검색·필터 등 가능한 탐색 맥락을 유지한다. 헤더에 테마와 별도로 Globe 아이콘 언어 메뉴를 둔다. 닫힌 메뉴에서는 언어명을 숨기고 메뉴를 열면 한국어·English 선택지를 표시한다.
- 버튼·상태·오류·빈 화면·폼 검증·관리자 UI 문구를 메시지 사전으로 관리한다. 문자열 결합으로 문장을 만들지 않고 복수형·날짜를 현지화한다.
- 공식 지원 상태는 언어별로 따로 판정하지 않는다. 동일 상태를 번역된 라벨로 표현한다.
- 앱 설명·최적화 요약 등 편집 콘텐츠는 locale별 번역 테이블로 관리한다. 상태·버전·근거는 공통 원본을 참조한다.
- 원문 변경 시 기존 번역을 검토 필요로 표시한다. 번역으로 지원 의미나 확정 수준이 바뀌지 않아야 한다.
- 번역 미완료 시 원문과 '원문으로 표시' 안내를 보여준다. 빈 내용이나 검증하지 않은 자동 번역을 공식 설명처럼 게시하지 않는다.
- 공식 인용은 원문을 보존한다. 번역을 제공하면 원문과 번역을 구별한다.
- 검색은 선택 언어뿐 아니라 등록된 한글·영문명·별칭을 함께 검색한다.
- 언어는 스토어 국가가 아니다. `/en`에서도 데이터는 한국 앱스토어 기준이며 이 기준을 표시한다. 미국 지원·배포로 추정하지 않는다.
- 언어별 title·description·canonical·hreflang 및 sitemap을 구성한다. 관리자·초안·불필요한 필터 조합은 검색 색인에서 제외한다.
- i18n 라이브러리는 Next.js App Router 호환성과 현행 문서를 확인해 설계 단계에서 선택한다. 한국어·영어 문구 길이 차이로 카드나 버튼이 깨지지 않게 한다.

## 6. 초기 데이터 수집

### 목표와 절차

1. 서로 다른 카테고리의 앱 약 10개로 API 응답, 한국 스토어 조회, 근거 확보 방식을 검증한다.
2. 공식 발표 앱, 국내 주요 앱, 넓은 화면 활용 앱을 합쳐 후보 약 200개를 선정한다.
3. 앱스토어 ID와 국가를 기준으로 중복을 제거하고 기본 정보를 수집한다.
4. 공식 출처를 조사하고 판정·확인 날짜·근거를 등록한다.
5. 검토한 앱 약 100개를 목표로 공개한다. 수집 실패나 미조사 앱을 숫자 충족을 위해 공개하지 않는다.

### 수집 원천

- 앱 발견: Apple 뉴스룸, 개발사 공식 발표, 운영자 선정, 사용자 제보.
- 기본 정보: Apple iTunes Search/Lookup API를 우선 검증한다.
- 지원 근거: 앱스토어 업데이트 내역·배지, 공식 공지·문서.

공개 API에서 듀오 최적화 앱 전체 목록이나 배지 전용 필드를 제공한다는 전제를 두지 않는다. 앱별 응답 필드와 현재 접근 가능성은 개발 시작 시 검증해야 한다. 한국 조회 결과가 없는 경우 다른 국가 데이터로 조용히 대체하지 않는다.

### 일괄 등록

관리자는 앱스토어 URL 목록 또는 CSV를 입력한다. CSV 열은 app_store_url, source_url, proposed_status, evidence_summary, announced_at, support_version을 제안한다. 기본 정보 자동 입력 후 행별 오류·중복·출처 누락을 보여주며 초안으로 저장한다. 같은 파일을 재실행해도 앱과 근거가 불필요하게 중복되지 않아야 한다.

API 응답에 존재하는 앱 이름·개발사·아이콘·카테고리·버전·릴리스 노트 등을 정규화하되 누락값을 허용한다. 공식 API 문서의 호출 제한과 자산 사용 조건을 확인하고, 방문자 요청마다 외부 API를 호출하지 않는다.

## 7. 계속 업데이트하는 운영 흐름

등록된 출처 정기 확인 → 변경 후보 생성 → 관리자 비교·검토 → 승인·보류·기각 → 승인 시 공개 상태와 이력 저장 → 공개 화면 캐시 갱신.

- 최초 제안 주기: 등록 출처 일 단위 확인, 신규 앱·공식 발표 주 단위 조사. 호출량·출처 특성에 따라 조정한다.
- 수집기는 출처별 어댑터로 분리한다. API와 일반 웹 문서를 동일한 파서로 처리하지 않는다.
- 수집 콘텐츠의 해시 또는 버전을 비교해 변경 후보 중복 생성을 막는다.
- 새 버전과 릴리스 노트는 별도 기록으로 보존한다. 지원 상태는 자동 변경하지 않는다.
- 한 번에 모든 앱을 실행하지 않고 작은 배치로 처리한다. timeout, 재시도 횟수, 지수 백오프, 실행 잠금 및 실패 기록을 둔다.
- 외부 요청 실패는 기존 공개 상태를 유지한다. 장기 실패는 관리자에 표시한다.
- 자동 수집으로 발견하지 못하는 신규 앱은 공식 발표 조사와 제보로 보충한다.
- 기각한 동일 콘텐츠는 새 근거가 없으면 다시 대기열에 올리지 않는다.

관리자는 기존 공개 정보와 변경 후보, 근거 문구·URL을 나란히 보고 처리한다. 승인은 지원 현황·근거 연결·이력·검토 상태를 하나의 DB 트랜잭션으로 반영한다. 정정은 이력을 삭제하지 않고 새 변경으로 기록한다.

## 8. 데이터 모델 초안

실제 SQL은 Spec Kit 설계 단계에서 확정하며 아래는 논리 모델이다.

| 테이블 | 주요 필드·역할 |
| --- | --- |
| apps | id, app_store_id, slug, 이름, 개발사, 카테고리, 별칭, 아이콘 URL, 발행 상태 |
| app_translations | app_id, locale, 표시 이름, 요약, 번역 상태·검수 시각; app_id+locale 유일 |
| app_store_listings | app_id, country, store_url, 현재 버전, 릴리스 노트, 조회 성공 시각; app_id+country 유일 |
| app_support | app_id, country, status, summary, support_version(nullable), reviewed_at, reviewed_by; app_id+country 유일 |
| support_features | app_id, country, feature_key, 설명, evidence_id |
| sources | URL, 출처 종류, 제목, 감시 여부, last_fetch_success_at, content_hash |
| evidence | source_id, 발표일, 짧은 발췌, 관련 버전·지역, 발견 시각 |
| app_evidence | app_id, evidence_id, 판정과의 관계; 다대다 연결 |
| review_items | app_id, candidate_payload, evidence_id, fingerprint, 검토 상태, 사유, 처리자 |
| support_history | app_id, country, before/after, 근거 ID, 변경 사유, 시각, 처리자 |
| submissions | 대상 앱/URL, 제보 종류·내용·근거, 처리 상태; 연락처는 초기 필수 수집하지 않음 |
| collection_runs | 대상 출처, 시도·성공 시각, 오류, 재시도 횟수 |
| admin_users | 관리자 user_id 및 권한; 일반 사용자가 수정 불가 |

- 하나의 Apple 발표가 여러 앱을 다룰 수 있어 근거와 앱은 다대다로 연결한다.
- app_store_id는 앱의 외부 식별자다. slug 변경 시 기존 URL을 리디렉션한다.
- 날짜는 UTC로 저장하고 초기 서비스는 Asia/Seoul 기준으로 표시하되 날짜 표기는 선택 언어의 형식을 사용한다.
- 기본 정보 갱신은 공식 지원 검토일과 공개 변경 정렬 기준을 갱신하지 않는다.
- 공개 이력에는 필요한 판정 정보만 노출하고 내부 검토 메모·관리자 개인정보는 제외한다.

## 9. 기술 구조·권한

Next.js가 공개 페이지와 관리자 UI·서버 동작을 담당한다. Supabase는 Postgres·Auth를 담당하고 Vercel에 배포한다. 공개 목록과 상세는 서버 렌더링 및 캐시를 활용하고 승인 직후 관련 캐시를 갱신한다. 초기 검색은 Postgres의 이름·별칭 검색으로 시작하며 별도 검색 엔진은 도입하지 않는다.

정기 작업은 Supabase Cron + Edge Functions를 기본 제안으로 둔다. Vercel 배포와 정기 실행 서비스 선택은 별개다. 구현 시 실행 시간·플랜 제한을 검증하며 장시간 단일 작업을 피한다. 스케줄러는 하나만 사용해 중복 실행을 방지한다.

- 방문자: published 앱과 공개 근거만 읽기 가능.
- 관리자: 인증된 사용자 중 admin_users로 허용한 계정만 편집 가능.
- 일반 로그인 성공만으로 관리자 권한을 부여하지 않는다.
- 노출되는 테이블에 RLS를 적용하고 초안·검토·수집·제보는 비공개다.
- service role/secret은 서버 전용이며 NEXT_PUBLIC 환경 변수에 넣지 않는다.
- 비회원 제보는 검증·속도 제한을 거친 서버 경로에서 접수한다. 제보 목록 공개 조회 금지.
- 수집 URL은 승인된 공식 도메인만 사용하고 내부 IP·로컬 주소 및 우회 리디렉션을 차단한다.
- 마이그레이션과 환경 변수 이름 목록을 저장소로 관리한다. 실제 비밀 값은 커밋하지 않는다.
- 로컬·Preview·운영 데이터를 분리하고 Preview에서 운영 정기 작업이 돌지 않게 한다.
- 환경 변수가 없어도 명확히 표시된 로컬 개발 fixture로 UI 확인 가능하게 하되 운영에는 fixture가 공개되지 않게 한다.

## 10. GitHub Spec Kit 개발 계획

프로젝트 공통 원칙을 먼저 정의하고 기능마다 명세 → 설계 → 작업 분해 → 구현 → 검증 순서로 진행한다. 설치한 Spec Kit 버전의 Codex 통합 방식과 명령은 공식 문서 및 CLI 도움말로 확인한다. 과거 버전의 명령 이름을 추정해 사용하지 않는다.

### 공통 원칙에 포함할 내용

1. 근거 없는 지원 판정을 만들지 않는다.
2. 자동 수집과 공개 승인 권한을 분리한다.
3. 공개 데이터, 초안, 비공개 운영 데이터를 분리한다.
4. 라이트·다크·모바일·한국어·영어를 동일한 완료 기준으로 다룬다.
5. 외부 연동 실패에도 기존 정보와 변경 이력을 보존한다.
6. DB 변경은 재현 가능한 마이그레이션으로 관리한다.
7. 실데이터와 개발 fixture를 명확히 분리한다.

### 기능 단위 개발 순서

| 단계 | 기능 명세 | 산출물 |
| --- | --- | --- |
| 001 | 디자인 기반·테마·다국어·앱 탐색 | 반응형 홈, 검색·필터, fixture, 두 테마, 언어별 URL·사전, 듀오 비주얼 자리 |
| 002 | 데이터 모델·관리자·근거 등록 | 마이그레이션, RLS, 관리자 로그인, 앱·근거 편집·공개 |
| 003 | 공개 DB 연동·앱 상세·이력 | 실제 데이터 조회, 상세, 업데이트 목록, 캐시 갱신 |
| 004 | 초기 데이터 가져오기 | API 검증, CSV 가져오기, 오류·중복 처리, 검토 데이터 축적 |
| 005 | 변경 감지·검토·제보 | 배치 수집, 검토 대기함, 승인·보류·기각, 제보 |
| 006 | 출시 검증·Vercel 설정 | 테마·권한·실패 시나리오 검증, 운영 환경 구성, 실제 콘텐츠 |

단계 001의 fixture를 공식 지원 현황으로 오해할 수 없게 로컬 개발 전용으로 표시한다. 초기 100개 조사 목표는 004~006에서 충족하며 001 구현을 막지 않는다.

## 11. 완료 기준 및 테스트

### 공개 탐색

- 한글·영문·별칭 검색, 복합 필터, 정렬, 페이지 이동, 뒤로 가기·공유 URL이 일관되게 동작한다.
- 초안은 검색·상세·사이트맵·공개 API에서 노출되지 않는다.
- 지원 상태마다 규정된 근거 또는 조사 사유와 최종 확인일을 표시한다.
- 존재하지 않는 앱, 조회 오류, 검색 결과 없음의 화면을 구분한다.

### 다국어

- 언어 선택 유지와 언어 URL 직접 접근이 충돌하지 않는다.
- 앱 상세에서 언어를 바꿔도 동일 앱을 유지한다.
- 영어 페이지에서도 한국 스토어 기준과 동일한 지원 판정이 표시된다.
- 번역 누락·원문 갱신·긴 영어 문구·날짜 표시를 검증한다.
- 번역되지 않은 키 문자열이 화면에 노출되지 않는다.
- 언어별 SEO 메타데이터와 공개 URL 연결을 검증한다.

### 운영 데이터

- 동일 CSV 재실행으로 앱이 중복 생성되지 않는다.
- 누락된 API 필드, 한국 스토어 결과 없음, 호출 제한과 timeout을 처리한다.
- 비관리자에게 직접 API를 호출해도 수정·비공개 조회가 허용되지 않는다.
- 승인 중 실패하면 공개 현황과 이력이 부분 저장되지 않는다.
- 수집 실패·문구 삭제·새 앱 버전만으로 지원 상태가 바뀌지 않는다.
- 반복 수집으로 같은 변경 후보가 중복되지 않는다.

### 디자인

- 대표 모바일·태블릿·데스크톱 폭에서 가로 넘침과 겹침이 없다.
- 첫 방문 OS 자동 연동, 단일 switch의 키보드 조작·상태, 수동 선택 저장 및 OS 미추종, 첫 로딩 깜빡임, 관리자 테마를 확인한다.
- 키보드 검색·필터·카드 이동 및 다이얼로그 초점이 정상이다.
- 최종 듀오 이미지의 출처·사용 조건 및 대체 텍스트를 기록한다.

유닛 테스트는 판정 검증·정규화·중복 방지 로직에, 통합 테스트는 RLS·승인 트랜잭션에 집중한다. E2E는 검색→상세와 관리자 검토→공개 갱신의 핵심 흐름을 확인한다. 외부 API 테스트에는 실제 응답 확인과 재현 가능한 fixture를 함께 사용한다.

## 12. 출시 기준과 운영 지표

- 검토한 앱 약 100개, 공식 지원 수는 실제 조사 결과대로 표시.
- 공개 앱의 공식 근거 또는 확인 필요 사유 충족률 100%.
- 최근 정보·빈 결과·제보·판정 기준 동선 작동.
- 수집 실패 확인 및 정정 방법 확보.
- 운영 권한과 비공개 데이터 접근 검증 완료.
- 최종 기기 자산, 모바일, 라이트·다크, 한국어·영어 화면 검토 완료.

초기 지표: 검색 결과 없음 비율, 자주 요청되는 미등록 앱, 공식 근거 확보 비율, 검토 대기 시간, 장기 미확인 앱 수, 수집 성공률. 트래픽 목표와 갱신 SLA는 운영 데이터를 보고 정한다.

## 13. 구현 전 확인할 사항

- 공개 도메인: 미정. 서비스명과 저장소명은 확정.
- 소개 문구: 본 문서의 개선 문구를 제안값으로 사용하며 변경 가능.
- 듀오 최종 이미지: 사용 가능한 공식 자산 또는 독자 목업 확보 필요.
- Apple API: 실제 앱 응답, 지역·필드·제한 검증 필요. 배지 수집 가능 여부 미확인.
- 관리자 계정과 Supabase 프로젝트·Vercel 프로젝트 연결: 개발 시 설정.
- 라이브러리 버전·인증 API·캐시 API·Spec Kit 명령: 구현 당시 공식 문서에 맞춰 선택하고 잠금 파일에 고정.
- 본 문서에는 검증된 초기 앱 데이터셋이 포함되어 있지 않다. 대화에서 예시로 언급된 앱을 그대로 지원 완료 데이터로 넣지 않는다.
